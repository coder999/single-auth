# single-auth: passkey (WebAuthn) support — design

**Date:** 2026-09-13
**Status:** Approved, pending implementation plan

## Problem

`single-auth` authenticates every consuming app with a username and a
bcrypt password (`Auth::attemptLogin()`). Passwords are phishable,
replayable, and the only factor. Passkeys (WebAuthn discoverable
credentials) are phishing-resistant by construction: the credential is
bound to a registrable domain by the browser, so a lookalike host cannot
elicit a usable assertion.

The goal is to add passkeys as a **second way in**, reusing the existing
session, identity, and CSRF machinery rather than building a parallel one.

## Non-goals

- **Not replacing passwords.** See "Additive" below. No account-recovery
  system is designed here, because none is needed.
- **No new authorization.** Unchanged from the 2026-08-12 design: this
  library answers "who is this", never "what may they do".
- **No cross-domain SSO.** Passkeys are bound to a registrable domain.
  That is a constraint to work with, not a problem to solve — see
  "RP ID" below.
- **No attestation verification.** We do not care which authenticator
  vendor a credential comes from; there is one human user and no
  enterprise policy to enforce. Attestation is requested as `none`.

## Decisions

### Additive, not a replacement

Passwords remain fully functional. A user may enrol one or more passkeys
and use either.

This is load-bearing for two reasons. It removes account recovery from
scope entirely — lose every device, log in with the password and enrol
again. And it means a defective passkey deploy cannot lock the operator
out of the admin panels used to fix it. The testing strategy below is
only defensible *because* of this.

### `Passkeys` composed with `Auth`

A new `src/Passkeys.php`, constructed with the PDO, an `Auth`, and an
`rp_id`. `Auth` gains exactly one new method, `loginAs(int $userId)`,
which regenerates the session id, sets `$_SESSION['user_id']` and stamps
`last_login`. `attemptLogin()` is refactored to call it.

The alternative — passkey methods directly on `Auth` — was rejected: it
roughly doubles that class and mixes two concerns, and every consumer
would pay passkey constructor options whether or not it uses them.

`loginAs()` establishes a logged-in session **without verifying any
credential**. That is a genuine footgun in a security library and there is
no package-private visibility in PHP to prevent misuse. It is mitigated by
an explicit doc block, and accepted because this library is already wholly
trusted code.

### `web-auth/webauthn-lib`

Chosen 2026-09-13 on maintenance rather than size. The alternative,
`lbuchs/WebAuthn`, is dependency-free and a better aesthetic fit for a
two-class library, but its last release was 2024-07-04 and its last commit
roughly a year before this decision, with 49 open issues. Depending on
dormant authentication code means inheriting its maintenance.

`web-auth/webauthn-lib` had released three days before this decision, has
a near-empty issue backlog, and ~22x the adoption, so defects surface
elsewhere first. The costs are real and accepted: 14 transitive
dependencies into a package whose `require` is currently only `php` and
`ext-pdo`, and a PHP floor moving from `>=8.1` to `>=8.2`. The floor bump
is free — every consumer already runs 8.4. `ext-json` and `ext-openssl`
are already present in the deployed PHP image.

### Discoverable credentials, user verification required

Registration requests `residentKey: required` and
`userVerification: required`. Login therefore needs no username typed:
click, touch the sensor, done. UV is required because every consumer of
this library gates administrative access.

## Data model

One migration adds a table and a column.

`user_credentials`:

| column | type | notes |
|---|---|---|
| `id` | INT UNSIGNED, PK | |
| `user_id` | INT UNSIGNED NOT NULL | FK → `users.id`, ON DELETE CASCADE |
| `credential_id` | VARCHAR(255) NOT NULL UNIQUE | base64url **text** |
| `public_key` | TEXT NOT NULL | |
| `sign_count` | INT UNSIGNED NOT NULL DEFAULT 0 | |
| `transports` | VARCHAR(255) NULL | e.g. `internal,hybrid` |
| `label` | VARCHAR(64) NOT NULL | user-supplied |
| `created_at` | DATETIME NOT NULL | |
| `last_used_at` | DATETIME NULL | |

`credential_id` and `public_key` are base64url/PEM **text**, not
`VARBINARY`. SQLite has no `VARBINARY`, and CLAUDE.md's portable-SQL rule
exists precisely so the suite runs against an in-memory SQLite PDO. Text
keeps one schema valid on both engines.

`users` gains `webauthn_user_handle VARCHAR(64) NULL UNIQUE`, holding
base64url of 32 random bytes. It is generated by `beginRegistration()`
when absent — it forms part of the credential creation options, so it
must exist before they are built, not after the ceremony completes. It is
then stable for the lifetime of the account: regenerating it would orphan
every already-enrolled credential.

The handle is stored on the user's device and returned by the
authenticator, so it must not be `users.id`: an incrementing integer
reveals how many accounts exist and correlates the same person across
unrelated sites. Nullable, so `users` stays column-compatible per
CLAUDE.md.

Challenges live in `$_SESSION` — single-use, 120-second TTL, cleared on
completion whether it succeeded or failed. Sessions are already
database-backed via `DbSessionHandler`, so this needs no new storage and
works across every consumer.

**This migration is safe to apply on its own.** A new table plus a
nullable column breaks no deployed code. Stated explicitly because the
README's warning about `20260813020513_rename_admin_tables` teaches the
opposite lesson.

## Library API

```php
final class Passkeys
{
    public function __construct(PDO $pdo, Auth $auth, array $options);
    // rp_id (required), rp_name, challenge_ttl = 120

    public function beginRegistration(int $userId, string $label): string;
    public function finishRegistration(int $userId, string $clientJson): bool;
    public function beginLogin(): string;
    public function finishLogin(string $clientJson): ?array;  // user row or null

    public function listCredentials(int $userId): array;
    public function deleteCredential(int $userId, int $credentialId): bool;
    public function hasCredentials(int $userId): bool;
}
```

### RP ID and origin validation

`rp_id` is the consumer's existing cookie domain without the leading dot,
so it needs no new configuration and cannot drift from the cookie scope.

An origin is accepted if and only if its scheme is `https` **and** its
host equals `rp_id` or ends with `.` + `rp_id`. That is the WebAuthn
specification's own rule, so there is no allowlist to maintain: an
`rp_id` of `marktuttlemd.com` automatically covers that domain and every
subdomain app on it.

There is deliberately **no option to relax this**. An earlier draft
carried an `insecure_origins` escape hatch so a plain-HTTP local origin
could be used in automated browser tests; dropping browser tests (see
Testing) removed the only reason for it to exist. The check is
unconditional.

A consequence, recorded so it is not rediscovered as a bug: **passkeys
cannot work in local development**, which is served over plain HTTP and
is therefore not a secure context.

### Sign counter

Some authenticators — notably iCloud Keychain — always report `0`. Rule:
if the stored and incoming counters are both `0`, skip the check;
otherwise require strictly increasing and reject as a possible cloned
credential if it is not. Store the new value on success.

### Throttling

`login_attempts` remains password-only. There is no shared secret to
brute-force on the passkey path.

## Consumer integration

Each consumer adds five small pieces. Taking `console` as the first:

| file | purpose |
|---|---|
| `lib/auth.php` | a `passkeys()` accessor, mirroring `auth()` |
| `passkey.php` | JSON endpoint: register begin/finish, login begin/finish |
| `passkey.js.php` | passthrough serving the library's JS asset |
| `login.php` | passkey button, shown only when supported |
| `passkeys.php` | enrolment: list, add, delete credentials |

CSRF applies to both register actions. `login/begin` issues a challenge
to an anonymous session, which is safe: a challenge is useless without a
credential.

### Why the JS is served through PHP

The browser half is ~80 lines of `navigator.credentials` plumbing plus
base64url helpers, identical in every consumer, so it ships **from the
library** rather than being copied four times. It is protocol plumbing,
not branding, so this does not contradict "no login-page HTML ships in
this package".

It cannot be served as a static file: every site's nginx config denies
`/vendor/` (added after `/vendor/composer/installed.json` was found
publicly readable in production, 2026-08-26), and Composer's install
target sits inside the webroot. Each consumer therefore serves it through
a ~10-line PHP passthrough with a `filemtime`-based cache-busting query,
matching the convention already used for that app's own assets.

### Authorization must be re-checked after a passkey login

Consumers may impose authorization on top of identity. `console` keeps an
allowlist and calls `console_user_allowed()` after every successful
password login, rendering 403 otherwise.

**A passkey login that omits that check is an authorization bypass** —
any identity in the shared `users` table would gain access. The check
therefore belongs inside a single consumer-side helper that both login
paths call, not duplicated into the new endpoint.

This generalises: every consumer integrating passkeys must confirm that
whatever it does after `attemptLogin()` also happens after
`finishLogin()`.

## Testing

The browser ceremony is verified **by hand in production**; the server
half is covered by automated tests. The split follows the failure modes:

- **Loud failures** — the button does nothing, the ceremony aborts, the
  endpoint 500s. Visible within seconds of manual use.
- **Silent failures** — an assertion is accepted when it should not be: a
  credential belonging to another user, a replayed challenge, an origin
  from the wrong domain, a cross-user credential deletion. These are
  indistinguishable from success by using the feature.

The second class lives entirely in the server half and is fully testable
with fixtures against in-memory SQLite. That is where the test effort
goes:

- origin accepted / rejected, including a subdomain and a lookalike host
- challenge TTL, and that a challenge cannot be replayed
- sign-counter regression rejected
- unknown credential rejected
- `listCredentials`/`deleteCredential` scoped to their owner
- `loginAs` establishes a session; `attemptLogin` behaviour unchanged
- consumer-side: a passkey login by a non-authorized identity is refused

Automated browser testing was considered and rejected. It would have
required either TLS in the local stack or a Chrome virtual authenticator
driven with an insecure-origin override — and the latter forced the
`insecure_origins` hole into the library. Dropping it removes that hole,
which is a net security improvement rather than a compromise. The risk is
acceptable only because the password path remains as a fallback.

`passkey.php` returns structured JSON errors so that a manual failure
yields something specific to diagnose.

## Rollout

1. **single-auth** — migration, `Passkeys`, `Auth::loginAs()`, tests, the
   JS asset, docs. Tag a minor release. Apply the migration by the
   documented production procedure.
2. **console** — first consumer. It sits on its own registrable domain,
   so a mistake cannot affect logins on the other apps, and it is the
   most recently built and most abstracted of the four.
3. **Verify in production**, then decide whether to continue.
4. **The remaining consumers** on the shared registrable domain. These
   share one RP ID, so enrolment happens **once**, in the app that already
   has an account-management page; the others need only a login button and
   the JS passthrough. This phase is substantially cheaper than phase 2.

Each consumer moves independently: Composer pins an exact commit, so
tagging a release changes nothing until a consumer bumps its constraint.
